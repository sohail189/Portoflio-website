The Problem

Manually screening resumes doesn't scale, and formats never match

Recruiters and hiring managers often deal with a large stack of resumes in inconsistent formats — some as PDFs, some as Word documents, some as plain text — with no easy way to quickly sort them by relevant job category. Manual screening is slow and inconsistent, and small teams rarely have a dedicated ATS to handle it.

The goal was to build a lightweight tool that could take a resume in almost any common format and immediately surface which job category it best fits, cutting the first pass of screening down from minutes to seconds.

My Approach

Turning unstructured resumes into a structured classification pipeline

The core challenge was normalizing wildly different file formats into clean text the model could actually reason about, then building a classifier reliable enough to trust for a first-pass filter.

  • Built format-specific parsers to extract raw text from PDF, DOCX, and TXT resumes into a single unified text pipeline.
  • Applied NLP preprocessing — tokenization, stopword removal, and normalization — to clean the extracted text before feature extraction.
  • Used TF-IDF vectorization to turn cleaned resume text into numerical features, then trained and compared classification models to assign resumes to job categories.
  • Wrapped the whole pipeline in a Streamlit app with drag-and-drop upload, so a recruiter can get a category prediction without touching any code.

The biggest lesson was that text extraction quality, not model choice, was the real bottleneck. A resume that extracts messily gives the model garbage to work with no matter how good the classifier is — so most of the engineering effort went into cleaning that first step.

What I Learned

Key takeaways

Classical NLP techniques like TF-IDF are still genuinely effective for well-scoped classification tasks like this one — they're fast, interpretable, and don't need heavy infrastructure to train or serve, which mattered for a project meant to be lightweight and easy to deploy.

Building for messy, real-world input (inconsistent resume layouts, varied formatting, scanned-looking text) taught me to think defensively about preprocessing from the start, rather than treating it as an afterthought once the model was working on clean sample data.
